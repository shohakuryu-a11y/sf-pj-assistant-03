# SF プロジェクトアシスタント

© 2026 Liu. All rights reserved.

SAP SuccessFactors の導入プロジェクトを支えるアシスタントです。今は次の 2 つの機能があります。

- **ビジネスルール設計**：ルールの作成・検証・履歴
- **データモデル管理**：データモデルの一覧・構造図・レコード・変更の書き出し

アプリを開くとホームが表示され、ここから各機能に移れます。サイドバーの分類（ビジネスルール設計・データモデル管理）は、ホームの機能の分類と同じです。

条件ロジックを自然な文章で書くだけで、そのまま設定に使える SAP SuccessFactors ビジネスルールの設計案が得られます。設計案で使っている項目・選択肢の値・Foundation Object / Generic Object / MDF / User のレコード・イベント事由・関数がテナントで使えるか、ルールとして成り立つか（書き込みの可否、event、分岐の矛盾など）、保守しやすいか（変数の使い方）、ルールシナリオ（Employee Central・Foundation Object・MDF）に合っているかを 5 つの分類・15 項目で検証します。

テナントのデータモデル（オブジェクト、項目のデータ型と参照先、アソシエーション、ピックリスト、レコード）は、SuccessFactors と同じ構造でアプリの中で管理できます。

**AI の API は一切呼び出さないため、無料で使えます。** 確定的な処理（概念の分解、項目の検索、プロンプトの組み立て、検証）はすべてアプリが行い、「ルールを設計する」部分だけを、普段使っている AI チャット（Claude、ChatGPT など）に任せます。プロンプトをコピーし、AI の回答を貼り付けると、アプリが自動で検証します。

> 画面の言語は日本語です。デモデータはすべて架空のテナント Demo Corp のもので、実在する顧客のデータは含まれていません。

## 1. クイックスタート

1. `index.html` をダブルクリックしてブラウザで開きます（インストールは不要です）
2. スタート画面が表示されたら、画面のどこかをクリックして開始します。ホームが表示されます
3. ホームの「ルールを作る」（または左の「ルール作成」）で入力例を 1 つクリック →「プロンプトを作成」→ ステップ 3 で「サンプルの回答を入れる」→「取り込んで検証」

AI を使わなくても、一連の流れを試せます。実際に使うときは、ステップ 3 を「プロンプトをコピー → AI チャットに貼り付けて送信 → 回答を貼り付ける」に置き換えます。

### 2.3 次の操作のガイド（レーザーの枠）

次に操作すべき入力欄やボタンの枠を、グリーンからティールに変わるレーザーが時計回りに周回し、やわらかい緑の光が広がります。光るのは常に 1 か所だけで、1 つ操作を終えると次の場所に移ります。

| 画面 | ガイドの順番 |
| --- | --- |
| ルール作成 | 要件の入力欄 →「プロンプトを作成」→「プロンプトをコピー」→ AI の回答の入力欄 →「取り込んで検証」→（エラーがある場合）「修正プロンプトをコピー」→ AI の回答の入力欄 →「取り込んで検証」…。検証に合格すると表示されなくなります |
| ルール検証（JSON） | JSON の入力欄 →「検証を実行」→（エラーがある場合）「修正プロンプトをコピー」→ JSON の入力欄 |
| ルール検証（文章） | ルール案の入力欄 →「変換プロンプトを作成」→「プロンプトをコピー」→「AI の回答を貼り付ける」 |
| データモデル | オブジェクト・項目・ピックリスト・値・レコードを変更すると「保存」が光ります。追加の画面では、ID（コード）とラベル（名称）を入力すると「追加する」が光ります |

### 2.4 ルール作成（要件からルールを作る）

4 つのステップで進めます。終わったステップは番号が緑になります。

| ステップ | 機能 |
| --- | --- |
| 1 要件を入力 | 業務上の要件を入力します。下のボタンで入力例を入れられます。**ルールの種類（任意）**で、ルールシナリオ（「2.9 ルールシナリオ」）を指定できます。既定は「AI に選ばせる」です。シナリオを指定すると、プロンプトでそのシナリオを使うように指示し、シナリオの base object（入社・再入社の Employee Information など）をプロンプトに含めます |
| 2 AI に送る | **ローカル解析の結果**：見つかった概念、候補の項目とその理由（項目名・同義語のほか、選択肢やレコードの名称からも探します。例：「東京本社」→ 勤務地）<br>**プロンプトに含めるデータ**：「データモデル全体を含める」がオンのときは全体を含めます。オフのときは、下で選んだオブジェクトだけを含めます（最初は要件に関係しそうなオブジェクトが選ばれています）。各オブジェクトの使える event・アクセスできるオブジェクト・クロスエンティティ、各項目のデータ型と参照先・必須・読み取り専用、参照先のレコード（無効・期間外の印付き）もプロンプトに入ります<br>**AI への指示**：データの正しい使い方のほか、「保守しやすいルールにすること」（繰り返す計算や判定値は変数 variables にまとめる、変数名と説明の付け方、重複を作らない）と「日本語について」（文章は文法の正しい自然な日本語で、中国語の単語・簡体字を使わない。誤りやすい語の例つき）を必ず含めます。プロンプトに含めるオブジェクトの種類に合わせて、**ルールシナリオの表**（シナリオごとの base object・Model・event・アクション・注意点。MDF を含むときは目的の表も）を入れ、AI に scenario を選ばせます。修正プロンプト・変換プロンプトにも同じ指示が入ります<br>**プロンプトを表示**：プロンプト全文と文字数を確認できます<br>**プロンプトをコピー** / **共有**（ブラウザが対応している場合のみ表示） |
| 3 AI の回答を貼り付け | AI の回答を貼り付けます（説明文が含まれていても、JSON の部分だけを取り出します）。入力例を使った場合は「サンプルの回答を入れる」が表示されます |
| 4 検証結果 | **判定とチェック項目の一覧**：合格 / 問題の件数・合格した項目数・注意の件数を表示します。判定をクリックすると 5 つの分類が開き、分類をクリックするとその分類のチェック項目（15 項目）と結果が開きます。もう一度クリックすると閉じます。合格・不合格にかかわらず一覧を開けます。エラーがあるときは、判定とエラーのある分類が最初から開いています。エラーは赤、注意はオレンジで表示します（詳しくは「2.8 バリデーター」）<br>**ルール**：VAR（変数）/ IF / ELSE IF / THEN / ELSE のルールカード。ルールシナリオ・目的・base object（Model）・event を上部に表示します。項目は「オブジェクト.項目」と ID で表示されます。値の設定のほか、必須・表示、メッセージ（重要度・文・Message Definition・パラメーター）、レコードの作成・削除、ワークフローも表示します<br>**設定方法**：ルールシナリオ（設計案にないときは推定）、目的、base object、event と、SuccessFactors でルールを作って割り当てる手順（Configure Business Rules でシナリオを選ぶ → ルールを設定 → 割り当てる場所）、シナリオの注意点。メッセージやワークフローを使うときは、先に作る設定も表示します<br>**前提**：AI が置いた解釈の前提<br>**項目の解決**：要件の言葉と項目の対応、種類（直接対応 / 近い項目 / 派生概念）、確信度のバー。70% 未満の場合は候補の確認を促します<br>**新規に必要な設定**、**リスク**<br>**修正を依頼する**（エラーか注意がある場合）：「修正プロンプトを表示」で全文を確認、「修正プロンプトをコピー」/「共有」<br>**JSON をコピー**、**新しい要件**（最初からやり直す） |

「取り込んで検証」を実行するたびに、結果は合否にかかわらず履歴に自動保存されます。

### 2.5 ルール検証（既存の設計案を検証する）

上部で 2 つのモードを切り替えます。

| モード | 機能 |
| --- | --- |
| JSON・AI の回答 | JSON または AI の回答全体を貼り付けて「検証を実行」。結果の表示はルール作成のステップ 4 と同じです。エラーがある場合は「修正プロンプトを表示」で全文を確認し、「修正プロンプトをコピー」/「共有」できます。「履歴に保存」で手動保存します。入力欄の上のボタンで、テスト用のサンプルを入れられます：誤りを含むサンプル、紛らわしい項目（正しい選択／取り違え）、型の違う項目（関数で変換／変換なし）、MDF（資格手当・Evaluate）、Foundation Object（部署）、入力チェック（メッセージ）。詳しくは「3.8 テスト用のサンプル」を参照 |
| 文章のルール案 | 文章で書いたルール案を貼り付けて「変換プロンプトを作成」→ 変換用プロンプトを表示・コピー・共有 → AI の回答を貼り付けるときは「AI の回答を貼り付ける」をクリックすると、JSON モードに切り替わります |

### 2.6 履歴

| 機能 | 説明 |
| --- | --- |
| 一覧 | 件数と、各履歴のタイトル・日時を表示します。合格／不合格のアイコンは、毎回**現在のデータモデル**で検証し直した結果なので、データモデルを変えると（例：レコードを無効にすると）結果も変わります。最大 50 件まで保存されます |
| 詳細 | 行をクリックすると開きます：要件の原文、検証し直した結果の全体、「JSON をコピー」、「修正プロンプト」（エラーがある場合、コピー）、「この履歴を削除」 |
| 1 件削除 | 行の右端のゴミ箱をクリック → 赤い「削除」に変わる → 3 秒以内にもう一度クリックで削除。クリックしなければ 3 秒で元に戻ります |
| すべて削除 | 一覧の下の「すべての履歴を削除」。同じく 2 回クリックで確定します |

削除した履歴は元に戻せません。

### 2.7 データモデル

SuccessFactors のデータモデルを、同じ構造でアプリの中に再現して管理します。ルールの検証は、すべてここにあるデータで行います。

データモデルは 2 つのレイヤーでできています。**同期レイヤー**（`data/catalog.js`、全員で共有）と、**変更ログ**（アプリで行った変更。このブラウザにだけ保存）です。画面に表示されるのは「同期レイヤーに変更ログを順に適用した結果」です。各要素には出どころを示すラベルが付きます：ラベルなし = 同期、「変更済み」= 変更あり、「手動追加」= 手動で追加、「無効」= 無効化済み。

**管理できるもの（SuccessFactors の対応する機能）**

| 要素 | 内容 | SuccessFactors で対応するもの |
| --- | --- | --- |
| オブジェクト | 業務上の意味の説明と同義語、種類（Employee Central / Foundation Object / Generic Object / カスタム MDF / ユーザー）、状態、有効日付（Effective Dating）、キー、base object にできるか、使える event、クロスエンティティ（値を設定できる他のオブジェクトと event） | Succession Data Model の HRIS 要素、Configure Object Definitions |
| 項目 | データ型（テキスト、翻訳可能テキスト、整数、小数、日付、日時、はい/いいえ、選択肢、Foundation Object、Generic Object、ユーザー、自動採番、添付ファイル）、参照先（Valid Values Source）、親項目（カスケード）、必須、読み取り専用、最大長、小数桁数、状態、説明、同義語 | HRIS 項目、MDF の Fields |
| アソシエーション | 名前、参照先、多重度（1:1 / 1:n）、種類（アソシエーション / コンポジット / Valid When） | MDF の Associations |
| ピックリスト | ID、ラベル、業務上の意味の説明と同義語、状態、親 picklist。値ごとにコード、ラベル、状態、親の値 | Picklist Center（カスケード picklist を含む） |
| レコード | Foundation Object・Generic Object・MDF・User のデータ。コード、名称、状態、有効開始日・終了日、項目の値（選択肢や参照先はリストから選択） | Manage Organization, Pay and Job Structures、Manage Data、ユーザー |

項目の参照先（Foundation Object・Generic Object・User）とアソシエーションは、そのままルールでたどれる範囲（ナビゲーション）になります。たとえば職務情報の「部署」（Foundation Object → FODepartment）を通じて、部署の「部署長」（User）を参照できます。

**データモデルのトップ**

| 機能 | 説明 |
| --- | --- |
| 一覧 / 構造図 | 左上のスイッチで切り替えます。一覧はこれまでどおりのリスト表示、構造図はつながりを図で表示します（後述の「構造図」）。最後に使った表示を覚えています |
| オブジェクト / ピックリスト | 一覧の上部で切り替えます。オブジェクトは種類ごとに、項目数・レコード数・変更数を表示します |
| 検索 | オブジェクト、項目（ラベル・同義語・英語ラベル・ID・説明）、ピックリストと値、レコード（コード・名称）をまとめて検索します |
| 「追加」 | オブジェクトまたはピックリストを追加します |
| 「管理」 | 管理パネルを開きます（後述） |

**構造図**

オブジェクトとピックリストが、どの項目・アソシエーションでつながっているか、ルールでどこまでたどれるかを、黒い方眼の画布に図で表示します。「データモデル」の左上のスイッチで「構造図」を選ぶと開きます（「一覧」で元のリスト表示に戻ります）。

つながりは、バリデーターと同じデータモデル（このブラウザでの変更を含む）から作ります。base object からたどれる範囲と経路も、バリデーターの判定（「base object にしたときアクセスできるオブジェクト」）と同じ計算です。そのため、図でたどれるオブジェクトはルールでも参照でき、図でたどれないオブジェクトはバリデーターでもエラーになります。

初めて開いたときの図は空です。上部の検索で、見たいオブジェクトまたはピックリストを選ぶと図に表示され、そこから支線を開いてつながりをたどります。図に出した節点は、いつでも図から外せます。

*こんなときに使います*

| やりたいこと | 使い方 | 結果 |
| --- | --- | --- |
| あるオブジェクトが何とつながっているかを知りたい | 節点をクリックして支線を開く。右の詳細パネルの「参照先」「アソシエーション」「参照元」を見る | 参照項目・アソシエーションでつながるオブジェクトが周りに広がり、どの項目でつながっているかが線の名前とパネルに出る |
| ルールで、base object から別のオブジェクトの項目を使えるか確かめたい | BASE で base object を選び、目的のオブジェクトをクリックする | たどれれば経路（例：`EmpJob.department.headOfUnit`）と段数が出る。たどれなければ、段数以内に経路がないことが表示される |
| 1:n（集合）になるかどうかを知りたい | BASE を選んで節点のバッジを見る | 「集合」のバッジが付いた節点は、途中に 1:n があるため、集合フィルターか集計関数が必要 |
| クロスエンティティで値を設定できるオブジェクトを知りたい | BASE で職務情報などを選ぶ | 「書き込み可」のバッジと緑の流れる破線で示される |
| 項目がどのピックリストを使い、カスケードの親子がどうなっているか知りたい | 上部の「ピックリスト」をオンにして節点を開く | 黄色のカプセル形のピックリストと、カスケードの親への点線が出る |
| データモデル全体を見渡したい | 「全件を種類別に表示」 | すべてのオブジェクトが種類ごとの列に並び、その間の線がすべて描かれる |
| 登録したアソシエーションや参照項目が正しくつながったか確かめたい | 詳細画面で追加・変更してから構造図に戻る | 変更がすぐ図に反映される（線が増える・消える） |

*支線の開閉*

- 節点をクリックすると、上部の関係のボタンでオンになっている関係でつながるオブジェクト（支線）のうち、まだ図にないものを開きます。新しい節点は、親から外側に向かって扇形に広がり、ほかの節点と重ならない位置に置かれます（親のない節点、たとえば検索で出した節点では、周り一周に並べます）
- 開いた節点をもう一度クリックすると、その節点から開いた支線を、その先の支線ごとすべて閉じます
- 節点の右の「+数字」は、まだ開いていない支線の数です。「−」は、すべて開いていて閉じられる状態です。どちらも出ていない節点には、開ける支線がありません。その節点をクリックすると「これ以上開ける支線はありません」と表示され、詳細パネルだけが開きます
- 「参照元」をオンにすると、そのオブジェクトを参照しているオブジェクト（逆向きのつながり）も開きます。オフのときは、そのオブジェクトから出ていくつながりだけを開きます
- 関係のボタンをオフにすると、その種類の線は図から消えます（節点は残ります）。オンに戻すと線も戻ります

*節点の見方*

| 表示 | 意味 |
| --- | --- |
| 角の丸いカード | オブジェクト。上の色の帯とラベルの略号が種類です：EC（Employee Central、青）、FO（Foundation Object、緑）、GO（Generic Object、青緑）、MDF（カスタム MDF、橙）、USR（ユーザー、紫） |
| 黄色のカプセル形 | ピックリスト（PL）。ID と値の数を表示します |
| カードの中の数字 | 「項目 n」＝項目の数、「関係 n」＝参照項目・アソシエーション・クロスエンティティでつながる先の数、「PL n」＝使っているピックリストの数 |
| 点線の枠で薄い | 無効のオブジェクト・ピックリスト |
| 白いカード | BASE で選んだ base object |
| 灰色で薄い | BASE を選んでいるとき、base object からたどれないオブジェクト |
| 「n 段」のバッジ | base object から n 段でたどれる |
| 「集合」のバッジ（橙） | 経路の途中に 1:n があり、集合として扱う（集合フィルターか集計関数が必要） |
| 「書き込み可 · 1 段」のバッジ（緑） | クロスエンティティで値を設定できる |

*線の見方*

| 線 | 関係 |
| --- | --- |
| 灰色の実線 | 参照項目（Foundation Object・Generic Object・ユーザーを参照する項目）。同じ相手を参照する項目が複数あるときは 1 本にまとめ、「項目名 ほか n」と表示します |
| 青の破線 | アソシエーション |
| 青の太線 | コンポジット |
| 青緑の点線 | Valid When |
| 緑の流れる破線 | クロスエンティティ（値を設定できる先） |
| 細い黄色の線 | 項目が使うピックリスト。黄色の点線はカスケードの親ピックリスト |
| 先が矢印 | 1:1 |
| 先が三つ又 | 1:n（集合） |
| 線の上を流れる点 | たどる向き（参照する側 → 参照される側）。節点を選んだとき・マウスを乗せたときに、その節点の線の上に流れます（クロスエンティティの破線は常に流れます） |
| 緑の太線 | BASE からの経路（選んだ節点までの道筋） |

同じ 2 つのオブジェクトの間に複数の線があるときは、重ならないように少しずつ曲げて描きます。

*BASE（base object からたどれる範囲）*

- 上部の BASE で、base object にできるオブジェクトを選ぶと、図を作り直し、そのオブジェクトを中心に、ルールでたどれるオブジェクトをすべて並べます。中心から 1 段目・2 段目・3 段目の同心円に置き、円には「n 段目」と表示します（段数は設定のたどれる段数 `navDepth` まで。既定は 3）
- たどれるかどうかの判定はバリデーターと同じです：有効な参照項目とアソシエーションを段数までたどり、クロスエンティティの対象は 1 段目に置きます。1:n を通らない経路があれば、そちらを優先します
- 中心以外の節点を選ぶと、base object からその節点までの経路を緑の太線で示し、詳細パネルの「（base object）からの経路」に次の 3 つを表示します
  - 経路の図：オブジェクトと、経由する項目 ID（1:n なら `[1:n]`）を順に並べたもの。項目 ID にマウスを乗せると項目名が出ます
  - 経路の式：`EmpJob.department.headOfUnit` のような、ID をつないだ形
  - 説明：何段でたどれるか、集合として扱う必要があるか、クロスエンティティで値を設定できるか
- たどれないオブジェクトを選ぶと「n 段以内に経路がないため、ルールからは参照できません」と表示されます
- BASE の状態でも、節点のクリックで支線を開閉できます。閉じると、その節点を経由する先の節点が消えます
- 詳細パネルの「base object にする」でも BASE を切り替えられます
- BASE を「（指定しない）」に戻すと、節点はそのまま残り、段数のバッジと同心円が消えます

*詳細パネル*

| 対象 | 表示する内容 | ボタン |
| --- | --- | --- |
| オブジェクト | 種類、ラベル、ID、業務上の意味の説明、項目数・レコード数・base object にできるか、（BASE のとき）base object からの経路、使える event、参照先（項目）・アソシエーション・クロスエンティティ・ピックリスト・参照元の一覧（それぞれ件数と、経由する項目 ID） | 詳細を開く、base object にする（base object にできるオブジェクトのみ）、中央に表示、図から外す |
| ピックリスト | ラベル、ID、説明、値の数・使っている項目の数・親ピックリストの有無、カスケードの親と子、使っている項目の一覧 | 詳細を開く、中央に表示、図から外す |

一覧の行をクリックすると、その節点が図になければ選んでいる節点の近くに出し、選んだ状態で画面の中央に移動します。

*そのほかの機能*

| 機能 | 効果 |
| --- | --- |
| 検索 | 入力するとオブジェクトとピックリストの候補が出ます。選ぶ（またはラベル・ID を入力して Enter）と、その節点を図に出して、選んだ状態で中央に移動します。節点を選んでいるときはその近くに、何も選んでいないときは今見えている画面の中央に置きます。すでに図にある節点なら、そこへ移動します。ピックリストを選んだときは「ピックリスト」の関係を自動でオンにします。何もない図の案内の「検索する」を押すと、検索欄に移ります |
| 全件を種類別に表示 | まだ図に出ていないものも含めて、すべてのオブジェクトを図に出し、Employee Central → ユーザー → Foundation Object → Generic Object → カスタム MDF の順に、種類ごとの列（多い種類は複数の列）に並べます。オブジェクト同士の線がすべて描かれるので、全体を見渡すときに使います。BASE を選んでいた場合は解除します |
| 図を空にする | 図からすべての節点を外し、何もない状態に戻します。BASE も解除します。データモデルは変わりません |
| ミニマップ | 図全体の縮図です。節点は種類の色の四角、緑の枠が今見えている範囲です |

*保存と反映*

- 表示中の節点と位置、関係のボタンの状態、BASE、表示の位置と倍率は、このブラウザに保存され、次に開いたときに同じ状態で表示します。初めて開いたときと「図を空にする」のあとは、何もない図から始まります
- 詳細画面でオブジェクト・項目・アソシエーション・ピックリストを変更して構造図に戻ると、つながりを作り直します。削除したオブジェクトの節点は図から消えます

*画面の幅が狭いとき（iPhone 表示・スマートフォン）*

- 凡例とミニマップを隠し、拡大・縮小などのボタンだけを右下に残します
- 詳細パネルは画面の下半分に表示します
- 上部のバーは、左右にスワイプしてすべてのボタンを使えます

*図に描かないもの*

- 無効の項目による参照（無効の項目はルールで使えないため）
- 権限（Role-Based Permissions）、国別のデータモデル（jobInfo_DEU など）、表示設定。バリデーターと同じく、データモデルに登録された範囲だけを描きます

**オブジェクト**

| 操作 | 説明 |
| --- | --- |
| 表示 | 業務上の意味（説明・同義語）、オブジェクト定義、項目、アソシエーション、**base object にしたときアクセスできるオブジェクト**（経路・段階数・1:n かどうか・クロスエンティティ）、このオブジェクトを参照している項目、レコード、変更履歴 |
| 追加 | ID、ラベル、業務上の意味の説明、同義語、種類、状態、有効日付、base object にできるか、使える event、クロスエンティティ、アソシエーションを入力して「追加する」。MDF・Generic Object・Foundation Object では、SuccessFactors と同じく標準項目（コード、有効開始日、名称、ステータス）を自動で作ります |
| 編集 | 「編集」から ID 以外のすべての属性を変更して「保存」。アソシエーションは追加・削除できます |
| 削除 | 「このオブジェクトを削除」を 2 回クリックします。同期レイヤーのオブジェクトは「管理」から復元できます。手動で追加したオブジェクトは、項目とレコードを含めて完全に削除されます |

**項目**

| 操作 | 説明 |
| --- | --- |
| 追加 | オブジェクトの画面の「項目を追加」。データ型を選ぶと、必要な入力欄（ピックリスト、参照先オブジェクト、親項目、最大長、小数桁数）が表示されます |
| 編集 | ラベル、必須、読み取り専用、最大長、小数桁数、状態、説明、同義語などを変更して「保存」。同期データの項目は、SuccessFactors と同じく作成後にデータ型と参照先を変更できません |
| 削除 | 手動で追加した項目のみ。同期データの項目は無効化します |

**ピックリストとレコード**

| 操作 | 説明 |
| --- | --- |
| ピックリスト | 業務上の意味（説明・同義語）、値の一覧、子のピックリスト（カスケード）、使っている項目を表示します。「値を追加」「編集」で値やリストの属性を変更します。使わなくなった値は削除せず無効化します |
| レコード | オブジェクトの画面の「レコード」から一覧（有効・無効・期間外の件数）を表示し、追加・編集・削除します。無効や有効期間外のレコードをルールで使うと、バリデーターがエラーにします |

**業務上の意味（意味の説明・同義語）**

オブジェクト・ピックリスト・項目のそれぞれに、業務上の意味の説明と同義語を登録できます（各画面の「編集」）。登録した内容は次のように使われます。

| 使われる場所 | オブジェクト | ピックリスト | 項目 |
| --- | --- | --- | --- |
| AI に送るプロンプト | 意味と同義語をオブジェクトの見出しの下に書く | 意味と同義語を値の一覧の前に書く | 意味と同義語を項目の行に書く |
| ルール作成のローカル解析 | ラベル・同義語が要件にあれば「見つかったオブジェクト」に出し、プロンプトに含めるオブジェクトの候補にする | ラベル・同義語が要件にあれば、そのピックリストを使う項目を候補にする | ラベル・同義語が要件にあれば候補にする |
| データモデルの検索 | 対象 | 対象 | 対象 |
| バリデーター（用語の照合） | — | — | 対象 |

似た名前で意味が違うものや、同じ意味で名前が違うものは、意味の説明で「〜とは別」と区別を書いておくと、AI が取り違えにくくなります。

すべての変更は変更履歴に記録され、「取り消す」で元に戻せます（同じ場所をその後に変更していない場合）。

**管理パネル**

| 機能 | 説明 |
| --- | --- |
| 集計 | テナント、同期データのバージョン、オブジェクト・項目・ピックリストの変更 / 手動追加 / 削除の数、レコードの変更数、変更ログの件数 |
| 削除したオブジェクト | 削除した同期レイヤーのオブジェクトの一覧。「復元」で元に戻せます |
| catalog.js を書き出す | すべての変更を反映したデータモデル全体を書き出します。リポジトリの `data/catalog.js` と置き換えると、全員に反映されます |

### 2.8 バリデーター（5 つの分類・15 項目のチェック）

チェックの結果は**エラー**（赤：ルールとして成り立たない、または SuccessFactors で設定できない）と**注意**（オレンジ：設定はできるが、意図どおりか確認が必要）に分かれます。エラーが 0 件なら合格です。

チェック項目は、**何を基準に判定するか**で 5 つに分類しています。各チェック項目は、ちょうど 1 つの分類に属します。

| 分類 | 判定の基準 | チェック項目 |
| --- | --- | --- |
| 記述の形式 | 設計案 JSON の書き方の決まり | JSON の構造、値の形式 |
| テナントのデータモデル | このテナントに実際にある項目・選択肢・レコード・イベント事由 | 項目の存在と有効性、データ型の一致、選択肢の値、参照オブジェクトの値、イベント事由 |
| SuccessFactors の仕様 | SAP SuccessFactors のビジネスルールの制約 | base object からのアクセス、関数の使い方、書き込み、event とトリガー、ルールシナリオ |
| ロジックと保守性 | 製品によらない、分岐の論理と書き方の品質 | 分岐のロジック、保守性 |
| 付帯情報 | ルール本体以外の記述（項目の解決・新規に必要な設定） | 付帯情報とデータモデル |

各チェック項目の内容は次のとおりです。

| チェック項目 | 主な内容 |
| --- | --- |
| JSON の構造 | 必要なキーがそろい、形式が正しい。不明なキーは黙って無視せず、エラーとして報告します。入れ子の空の条件グループもエラーです |
| 値の形式 | 日付は実在する "YYYY-MM-DD"、数値と true / false は引用符なし、整数の項目・引数に小数を入れていない、小数桁数・最大長を超えていない、null（空欄）を条件の比較に使っていない |
| 項目の存在と有効性 | 参照する項目とオブジェクトがデータモデルにあり、無効化されていない。ない場合は似た項目を提案します |
| base object からのアクセス | 項目のオブジェクトが、参照項目・アソシエーション・クロスエンティティを設定した段階数（既定 3）以内でたどれる。1:n でつながる集合の項目は、**集合フィルター**（`where`）で 1 件に絞るか、Cardinality・Sum of Collection Field Values などの集計関数の引数にしている。集合フィルターの左辺は集合のオブジェクトの項目、右辺は定数・選択肢・レコード・null・変数だけ（項目や関数は変数にしてから使う）。1 件に絞れない条件は注意（最初の 1 件だけが使われるため） |
| データ型の一致 | 比較・代入の両辺の型が一致し、ピックリストや参照先オブジェクトも一致している。参照項目を文字列で比較していない。eq / ne に複数の値を書いていない。日付と日時の混在は注意。整数の項目に小数になりうる値（小数の項目や To Number の結果）を設定していない。型が違う場合は、揃えるための公式の関数（To Number、Round、Format Number、Format、Substring + Create Date、Get Local Date of DateTime）を案内します |
| 選択肢の値 | picklist とコードが存在して有効である。カスケード picklist で、同じ分岐の親の値と子の値が一致している |
| 参照オブジェクトの値 | Foundation Object・Generic Object・MDF・User のレコードが存在し、有効で、有効期間内である（有効開始前は注意） |
| イベント事由 | イベント事由が存在して有効である。同じ条件で指定したイベントに、その事由が属している |
| 関数の使い方 | 関数が SAP SuccessFactors の公式のルール関数（関数表）にあり（公式にない関数は、近い名前の公式の関数を案内してエラー）、引数の数（省略可能・可変長を含む）と型が正しい。整数が必要な引数に、小数になりうる値を渡していない。Lookup の対象オブジェクトと項目が存在する |
| 書き込み | 設定先が読み取り専用・自動採番・添付ファイルではない。base object の項目か、クロスエンティティで許可されたオブジェクトの項目で、許可された event である。**Foundation Object の項目は、その Foundation Object 自身を base object にしたルールでだけ設定できる**（職務情報から部署の名称を設定するなどはエラー）。必須項目を空欄にしていない。値を設定できない event（onPostSave・saveAlert・onValidate・onDelete）で設定していない。MDF の目的 Evaluate の onSave で、externalCode などのキーを設定していない。**レコードの作成（Create）**：職務情報・報酬情報には Create を使わない（Set で新しいレコードができる）、クロスエンティティで Create を使える組み合わせと event、必須の項目の値がない場合は注意。**削除（Delete）**：職務情報は削除できない、集合のオブジェクトは削除するレコードを集合フィルターで指定している。**項目の必須・表示（プロパティ）**：base object の項目である、データモデルで必須の項目を「必須でない」にしていない、読み取り専用の項目を編集できるようにしようとしていない（注意）。onView で値を設定するときは、保存時に空欄に戻す onSave のルールも必要（注意） |
| event とトリガー | event が base object で使える（Foundation Object の onChange、MDF の onView のように SAP の仕様で使えないものは、理由も表示します）。onChange にはトリガー項目（trigger_field、なければ attach_to から推定）があり、base object の有効な項目で、ルールの中で使われている |
| ルールシナリオ | ルールシナリオ（`scenario`、「2.9 ルールシナリオ」）が base object・Model・event・アクションに合っている。MDF の Rules for MDF Objects では、目的（`purpose`）と event の組み合わせ（SAP の対応表）と、目的で使えるアクションも確認します。scenario・purpose がないときは base object の種類・event・アクションから推定して検証し、注意を出します。そのほかの主な確認：Employee Central で項目の必須・表示を設定するには Model の base object（`"model": true`）が必要、Employee Information は入社・再入社のシナリオだけ、イベント事由の自動設定で設定できるのはイベント事由とイベントだけ（空のときだけ設定する条件がなければ注意）、onInsert は有効日付のある MDF だけ。注意：Employee Central の警告・情報のメッセージはエラーとして扱われる、onChange のメッセージでは保存が止まらない、Rules for Metadata of MDF Objects は最新の People Profile でだけ有効、アラートや Execute のように設計案 JSON で書けないアクションのシナリオ |
| 分岐のロジック | 条件が矛盾していない、前の分岐に含まれて実行されない分岐がない、常に成り立つ分岐の後に分岐や ELSE がない、同じ分岐で同じ項目を異なる値に 2 回設定していない、onChange のトリガー項目自身を設定していない（繰り返し実行の恐れ） |
| 保守性 | 変数名が SAP の決まり（var_ で始まり、半角英数字とアンダースコア）に合い、重複せず、前に定義した変数だけを使っている。注意：変数の desc がない、使われない変数、中身が分からない変数名（var_1、var_tmp など）、同じ計算（関数）が 2 か所以上にある、同じ判定値（数値・日付）が 2 つ以上の条件にある |
| 付帯情報とデータモデル | 項目の解決（field_resolutions）の項目が存在してルールで使われている、確信度が 0〜1 で、70% 未満なら別の候補がある。new_config_needed と実際の項目が食い違っていない。メッセージ（raise）に Message Definition の code がなく、new_config_needed にも書いていなければ注意。**用語の照合**：要件の言葉（concept）が、データモデルでは別の項目のラベル・同義語として登録されていれば注意（kind が similar / derived で、その項目を alternatives に挙げている場合を除く）。手動追加した項目を使っている場合と、同期データが古い場合（既定 180 日）は注意 |

分岐のロジックは、条件を「または」で展開して項目ごとの値の範囲を比べる、安全側の判定です。判定できない条件（関数を使った条件など）では、矛盾や到達不能を報告しません。

### 2.9 ルールシナリオ

SAP SuccessFactors では、ルールを作るときに最初に**ルールシナリオ**を選びます。シナリオによって、base object・event・使えるアクション・ルールを割り当てる場所が決まります。アプリは SAP の公式ドキュメント（2611 版）に基づくシナリオの表（`data/knowledge.js` の `scenarios`・`mdfPurposes`）を持ち、設計案の `scenario` を検証します。

| 領域 | シナリオ（`scenario` の値） | base object | event | 設計案 JSON で使えるアクション |
| --- | --- | --- | --- | --- |
| Employee Central | 入社・再入社のルール（`ec_hire`：Trigger Rules for Hire/Rehire） | Employee Information（Model 可） | onInit・onChange・onSave | 値の設定、必須・表示、メッセージ |
| Employee Central | 入社・再入社の画面を開いたとき（`ec_hire_init`：Trigger onInit Rules for Hire/Rehire） | Employee Information Model | onInit | 値の設定、必須・表示 |
| Employee Central | 項目を変更したとき（`ec_change`：Trigger onChange Rules for HRIS Elements） | HRIS 要素（Model 可） | onChange | 値の設定、必須・表示、メッセージ |
| Employee Central | 保存するとき（`ec_save`：Trigger onSave Rules for HRIS Elements） | HRIS 要素（Model 可） | onSave | 値の設定、メッセージ、作成、削除 |
| Employee Central | 画面を表示するとき（`ec_view`：Trigger onView Rules for HRIS Elements） | HRIS 要素（Model 可） | onView | 値の設定（一時的な値）、必須・表示 |
| Employee Central | 入力チェック（`ec_validate`：Validate HRIS Elements） | HRIS 要素 | onChange・onSave | メッセージ |
| Employee Central | イベント事由の自動設定（`ec_erd`：Trigger Event Reason Derivation） | Job / Compensation Information Model | onSave | イベント事由・イベントの設定 |
| Employee Central | ワークフローの決定（`ec_wf`：Trigger Workflows） | HRIS 要素・Foundation Object | onSave | ワークフロー |
| Employee Central | クロスエンティティ（`ec_cross`：Trigger Cross-Entity Rules） | 職務情報・報酬情報・定期報酬・一時報酬・職務上の関係・雇用情報・退職情報 | onChange・onSave | 値の設定、作成、削除 |
| Employee Central | アラート（`ec_alert`）・職務情報の保存後のイベント（`ec_postsave`） | 対応する HRIS 要素 | saveAlert・onPostSave | 条件だけ（アラート・Execute は SAP の画面で設定） |
| Foundation Object | Foundation Object のルール（`fo_basic`：Basic） | Foundation Object | onInit・onSave（onChange は使えない） | 値の設定（自身の項目だけ）、メッセージ |
| MDF・Generic Object | MDF オブジェクトのルール（`mdf_objects`：Rules for MDF Objects） | MDF・Generic Object | 目的による（下の表） | 目的による |
| MDF・Generic Object | MDF の項目の必須・表示（`mdf_meta`：Rules for Metadata of MDF Objects） | MDF・Generic Object | onInit・onInsert・onChange・onLoad | 必須・表示 |

このほか、Employee Central の特定用途のシナリオ（Generate Employee ID for Hire/Rehire、Calculate Full-Time Equivalent、Off Cycle Event Batch など）は、base object と Model だけを確認します。

**MDF の目的（`purpose`）と event**（Rules for MDF Objects）

| 目的（`purpose` の値） | 割り当てられる event | 使えるアクション |
| --- | --- | --- |
| 初期値の設定（`initialize`） | onInit | 値の設定 |
| 入力チェック（`validate`） | onValidate・onSave・onPostSave・onDelete・onChange | メッセージ |
| 値の計算（`evaluate`） | onSave・onChange | 値の設定（onSave ではキーの項目を設定できない） |
| 状態に応じた値の更新（`stateUpdate`） | onInit・onInsert・onChange・onLoad | 値の設定 |
| MDF アラート（`alert`） | onPostSave | 条件だけ（アラートは SAP の画面で設定） |
| ワークフローの決定（`workflow`） | onSave・onDelete | ワークフロー |
| 画面の読み込み時（`onLoad`） | onLoad | 値の設定、メッセージ |

**Model の base object**（Employee Central）：Job Information Model のように、項目の値に加えて必須・表示も扱える base object です。設計案では `"model": true` と書きます。項目の必須・表示は Model の base object で、onInit・onChange・onView に設定します（onSave では設定しません）。

**Employee Information**：入社・再入社の画面で、まだ保存されていない個人情報・雇用情報・職務情報などをまとめて扱う base object です。データモデルに「社員情報（入社・再入社）」（`EmployeeInformation`）として登録しています。入社・再入社のシナリオでだけ使えます。

## 3. 操作ガイド（作業別）

### 3.1 要件からルールを 1 つ作る

1. サイドバーの「ルール作成」を開き、ステップ 1 に要件を入力します（または入力例をクリック）
2. 「プロンプトを作成」をクリックします
3. ステップ 2 で候補の項目を確認します。データモデルが大きい場合は「データモデル全体を含める」をオフにし、必要なオブジェクトだけを選びます
4. 「プロンプトをコピー」をクリックし、Claude や ChatGPT などのチャットに貼り付けて送信します
5. AI の回答を全部コピーしてステップ 3 の入力欄に貼り付け、「取り込んで検証」をクリックします
6. ステップ 4 の結果を確認します。特に「前提」と、確信度 70% 未満の「項目の解決」を確認してください。SuccessFactors での作り方と割り当てる場所は「設定方法」に表示されます
7. 結果は「履歴」に自動保存されます

### 3.2 エラーのある設計案を直す

1. 検証結果の下の「修正プロンプトを表示」で、内容を先に確認できます
2. 「修正プロンプトをコピー」をクリックし、**同じ** AI チャットに貼り付けます
3. AI が返した新しい回答を入力欄（ルール作成ではステップ 3、ルール検証では JSON の入力欄）に貼り付けて、もう一度検証します
4. 「検証に合格しました」と表示されるまで繰り返します

### 3.3 既存の JSON や文章のルール案を検証する

- **JSON**：「ルール検証」→「JSON・AI の回答」→ 貼り付け →「検証を実行」→ 必要なら「履歴に保存」
- **文章のルール案**：「ルール検証」→「文章のルール案」→ 貼り付け →「変換プロンプトを作成」→「プロンプトをコピー」して AI に送信 →「AI の回答を貼り付ける」→ 回答を貼り付け →「検証を実行」

### 3.4 履歴を見る・整理する

- 見る：「履歴」→ 行をクリック
- 1 件削除：行の右端のゴミ箱をクリックし、赤い「削除」をもう一度クリック
- すべて削除：一覧の下の「すべての履歴を削除」を 2 回クリック

### 3.5 データモデルをメンテナンスする

- **MDF オブジェクトを作る**：「データモデル」→「追加」→ ID（例：cust_Training）・ラベル・種類「カスタム MDF」などを入力 →「追加する」。標準項目が自動で作られます → 新しいオブジェクトの画面で「項目を追加」
- **別のオブジェクトや選択肢を参照する項目を作る**：「項目を追加」→ データ型を「選択肢（Picklist）」「Foundation Object」「Generic Object」「ユーザー」のいずれかにして、参照先を選ぶ。カスケードにするときは「親項目」も選ぶ
- **アソシエーションを追加**：オブジェクトを開く →「編集」→「アソシエーション」に名前・参照先・多重度・種類を入力 →「アソシエーションを追加」→「保存」
- **base object で使える event やクロスエンティティを変える**：オブジェクトを開く →「編集」→ チップで選択 →「保存」
- **選択肢の値を追加・無効化**：「ピックリスト」→ リストを開く →「値を追加」、または値を開いて「有効」をオフ →「保存」
- **部署や等級などのレコードを追加・無効化**：オブジェクトを開く →「レコード」→「レコードを追加」、またはレコードを開いて「有効」をオフ・有効終了日を入力 →「保存」
- **オブジェクトを削除・復元**：オブジェクトを開く →「編集」→「このオブジェクトを削除」を 2 回クリック。戻すときは「管理」→「削除したオブジェクト」→「復元」
- **項目に同義語を追加**：項目を検索 → 開く →「同義語」に追加 →「保存」。次回から、要件にその言葉が出てくると認識されます
- **変更を取り消す**：各画面の「変更履歴」で「取り消す」をクリック
- **つながりを図で確かめる**：「データモデル」→ 左上の「構造図」。節点をクリックして支線を開き、BASE で base object を選んで、目的のオブジェクトを選ぶと、ルールでたどる経路が表示されます

### 3.6 データモデルの変更を全員に反映する

1. 「データモデル」→「管理」→「catalog.js を書き出す」
2. ダウンロードしたファイルでリポジトリの `data/catalog.js` を置き換え、コミットしてデプロイします
3. アプリに戻り、「管理」→「この端末の変更をすべて消す」を実行します（新しい同期レイヤーと二重にならないようにするため）

別の PC で作業を続けるだけなら、「変更ログを書き出す（JSON）」と「変更ログを読み込む（JSON）」で十分です。

### 3.7 表示を調整する

- 背景の明るさ：サイドバー下部の緑の球をドラッグ。ダブルクリックで既定のグレーに戻ります
- 全画面表示：「全画面表示」をクリック、または `F11`
- iPhone 表示：サイドバー下部の「iPhone 表示」をクリック。戻すときはウィンドウ右上の「デスクトップ表示」
- 左上のマークを変更：正式なロゴのファイルを `icons/logo.svg` と `icons/logo-dark.svg` に置いて再読み込み

### 3.8 テスト用のサンプル

データモデルには、わざと紛らわしくした項目があります（詳しくは `demo_data/README.md`）。次のサンプルで、アプリの項目の選び方と型のチェックを確かめられます。

| サンプル | 場所 | 確かめること | 期待する結果 |
| --- | --- | --- | --- |
| 有期雇用の社員を雇い入れたとき… | ルール作成の入力例、ルール検証「紛らわしい項目：正しい選択」 | 「有期雇用」「就業場所」「雇止め予定日」「雇入れ日」「直属の上司」「所属組織の長」を、似た項目（社員区分、勤務形態、契約更新日、入社予定日、マトリクス上長、事業本部長）と取り違えずに選べるか。ステップ 2 の候補の項目で、正しい項目が上位に来るか | 合格・注意なし |
| 紛らわしい項目：取り違え | ルール検証 | 同じ設計で、社員区分・契約更新日・入社予定日・事業本部長を選んだ場合 | 型は合っているのでエラーなし。用語の照合で注意 4 件 |
| 旧人事システムから移行した社員プロファイル… | ルール作成の入力例、ルール検証「型の違う項目：関数で変換」 | 同じ名前・同じ意味で型が違う項目（入社日：文字列と日付、社員番号：整数と文字列、定年年齢：文字列と整数、勤続年数：小数と整数、最終等級変更日：日時と日付）を、関数で揃えて比較・代入できるか | 合格・注意なし |
| 型の違う項目：変換なし | ルール検証 | 同じ設計で関数を使わない場合 | エラー 8 件（データ型 5、関数 3）、注意 1 件（日付と日時の比較） |
| 保有資格を保存するとき… | ルール作成の入力例、ルール検証「MDF：資格手当（Evaluate）」 | MDF のルール（Rules for MDF Objects、目的 Evaluate、onSave）で、参照先の資格マスタの値を変数にして使えるか | 合格・注意なし |
| 部署を保存するとき… | ルール作成の入力例、ルール検証「Foundation Object：部署」 | Foundation Object のルール（onSave）で、メッセージと自身の項目の設定を使えるか | 合格・注意なし |
| 有期契約の職務情報を保存するとき… | ルール作成の入力例、ルール検証「入力チェック：メッセージ」 | 入力チェックのシナリオ（Validate HRIS Elements、onSave）で、Message Definition とパラメーター付きのメッセージを書けるか | 合格・注意なし |

### 3.9 構造図でつながりを調べる

1. 「データモデル」→ 左上の「構造図」。初めては何もない図が表示されます
2. **見たいものを出す**：上部の検索で、オブジェクトまたはピックリストを名前か ID で探して選びます。選んだ節点が図の中央に出ます
3. **つながりを見る**：出した節点をクリックして支線を開きます。続けて開いた先の節点をクリックすると、さらに先へたどれます。別のオブジェクトも見たいときは、また検索で出します。右の詳細パネルで、どの項目・アソシエーションでつながっているかを確認します
4. **ルールでたどれるか確かめる**：上部の BASE で、ルールの base object（例：職務情報）を選びます。目的のオブジェクトをクリックすると、経路（例：`EmpJob.department.headOfUnit`）と段数が出ます。「集合」のバッジがあれば集合フィルターか集計関数が、「書き込み可」のバッジがあればクロスエンティティでの設定ができます
5. **ピックリストも見る**：上部の「ピックリスト」をオンにしてから節点をクリックします
6. **全体を見る**：「全件を種類別に表示」で、すべてのオブジェクトを種類ごとの列に並べます。右下の「全体を表示」で画面に収めます
7. **詳しく見る・直す**：節点をダブルクリックすると、そのオブジェクトの画面が開きます。変更して戻ると、図に反映されます
8. **片付ける**：いらない節点は「×」（または Delete キー）で 1 つずつ図から外します。全部消すときは「図を空にする」

## 7. 設計案 JSON の形式

分岐の数は JSON の内容どおりに表示・検証されます。`branches` の 1 つ目が IF、2 つ目以降がすべて ELSE IF、`else` がどれにも当てはまらないときの処理です。

```json
{
  "intent": "入社時に、雇用区分に応じて試用期間終了日を設定する",
  "scenario": "ec_change",
  "base_object": "EmpJob",
  "event": "onChange",
  "trigger_field": "EmpJob.startDate",
  "attach_to": "職務情報 › 発令日の変更時",
  "branches": [
    {"if": {"all": [
       {"left": {"field": "EmpJob.event"}, "op": "eq", "right": {"picklist": "event", "codes": ["H"]}},
       {"left": {"field": "EmpJob.eventReason"}, "op": "in", "right": {"eventReasons": ["HIRNEW", "HIRMID"]}},
       {"left": {"field": "EmpJob.department"}, "op": "eq", "right": {"object": "FODepartment", "codes": ["D1100"]}}
     ]},
     "then": [{"set": "EmpJob.probationPeriodEndDate", "value": {"fn": "Date Plus", "args": [{"field": "EmpJob.startDate"}, {"const": 6, "type": "number"}, {"const": 0, "type": "number"}]}}]},
    {"if": {"any": [ ... ]}, "then": [ ... ]}
  ],
  "else": [{"set": "EmpJob.probationPeriodEndDate", "value": {"const": null, "type": "date"}}],
  "assumptions": [],
  "field_resolutions": [{"concept": "雇用区分", "kind": "similar", "ref": "EmpJob.employeeClass", "confidence": 0.86, "alternatives": []}],
  "new_config_needed": [],
  "risks": []
}
```

- 条件のグループ：`all`（かつ）または `any`（または）。互いに入れ子にできます（入れ子は空にしない）
- `op`：`eq` `ne` `in` `notIn` `gt` `lt` `ge` `le` `isNull` `isNotNull`。`eq` / `ne` の右辺は値 1 つ
- 値の書き方は 7 種類：`{"field"}`、`{"const","type"}`（`null` は空欄にする。set でだけ使う）、`{"picklist","codes"}`、`{"object","codes"}`（Foundation Object・Generic Object・MDF・User のレコード。User はユーザーID）、`{"eventReasons"}`（`{"object":"FOEventReason"}` と同じ）、`{"fn","args"}`（関数は入れ子にできます）、`{"var"}`（変数）
- 集合フィルター：1:n の集合の項目は `{"field": "PerEmail.emailAddress", "where": {"all": [{"left": {"field": "PerEmail.emailType"}, "op": "eq", "right": {"picklist": "ecEmailType", "codes": ["B"]}}]}}` のように、`where` で使うレコードを 1 件に絞ります。右辺には定数・選択肢・レコード・null・変数だけを使えます
- `scenario`：ルールシナリオ（「2.9 ルールシナリオ」の `scenario` の値）。`purpose`：Rules for MDF Objects（`mdf_objects`）の目的。`model`：Employee Central で Model の base object（Job Information Model など）にするときは `true`
- アクションは 6 種類：
  - 値の設定：`{"set": "オブジェクトID.項目ID", "value": 値}`
  - 項目の必須・表示：`{"property": "required", "field": "オブジェクトID.項目ID", "value": true}`、`{"property": "visibility", "field": "...", "value": "edit"}`（`edit` 表示・編集できる／`view` 表示だけ／`none` 表示しない）
  - メッセージ：`{"raise": "error", "message": "画面に表示する文", "code": "Message Definition の externalCode", "params": {"名前": 値}}`（`raise` は `error` / `warning` / `info`。文の中の `{名前}` にパラメーターの値が入ります）
  - レコードの作成：`{"create": "オブジェクトID", "values": {"項目ID": 値}}`
  - レコードの削除：`{"delete": "オブジェクトID", "where": 集合フィルターの条件}`
  - ワークフロー：`{"workflow": "Workflow Configuration のコード"}`
- `trigger_field`：event が onChange のときのトリガー項目（base object の項目）
- `variables`：分岐の前に計算しておく変数（SAP のルールの Variables セクション）。`{"name": "var_...", "value": 値, "desc": "説明"}` の配列で、条件・アクション・後の変数から `{"var": "var_..."}` で参照します。名前は `var_` で始め、半角英数字とアンダースコアだけ
- AI がよく使うほかの書き方も受け付けます：`if` / `then` / `else`、または `if` / `then` と `else_if` のリスト。どちらも自動で分岐に変換されます
- 不明なキーは黙って無視せず、エラーとして報告します

## 8. 注意事項

- 外部の AI サービスにプロンプトを貼り付けると、プロンプトに含まれるデータモデルの情報（項目、選択肢、レコードの名称など）も送信されます。実在する顧客のメタデータを使う前に、契約と社内規程を確認してください。
- 検証に合格しても、保証できるのは「アプリのデータモデルの範囲で、ルールとして成り立つこと」までです。データモデルがテナントの実際の設定と違えば結果も違います。また、要件の意図とルールの内容が合っているか（業務ロジックの正しさ）は判定できません。テスト用テナントで確認してください。
- 種類ごとの event・ルールシナリオ・MDF の目的とクロスエンティティの Create の組み合わせは、SAP の公式ドキュメント（Implementing Employee Central Core・Implementing the Metadata Framework、2611 版）に基づきます。オブジェクトごとのクロスエンティティの対象は、デモの設定です。関数表も SAP の公式ドキュメントに基づきますが、リリースによって関数が追加・変更されることがあります。実際のプロジェクトでは、テナントの設定と SAP の最新のドキュメントに合わせて `overlay.json` と `data/knowledge.js` を見直してください。
- Deloitte のロゴを使う場合は、正式なファイルを使い、ブランドガイドラインに従ってください。
- 本プロジェクトは SAP SE とは関係がなく、SAP SE の承認も受けていません。SAP および SuccessFactors は、ドイツおよびその他の国における SAP SE の商標または登録商標です。

## 9. できること・できないこと

### できること

- 業務の要件（文章）から、AI チャットに送るプロンプトを作り、AI が返した設計案（JSON）をアプリの中のデータモデルで検証する
- 文章で書いたルール案を JSON に変換するプロンプトを作り、変換後の JSON を検証する
- 設計案の誤りを直すための修正プロンプトを作る
- 設計案を、ルールカード（VAR / IF / ELSE IF / THEN / ELSE）と、SuccessFactors での作り方・割り当てる場所（設定方法）で表示する
- SuccessFactors と同じ構造のデータモデル（オブジェクト・項目・アソシエーション・ピックリスト・レコード）を、アプリの中で管理する

### できないこと（できると思われやすいもの）

| 分類 | できないこと | 代わりの方法・補足 |
| --- | --- | --- |
| SuccessFactors との連携 | テナントに接続しない。ルールの登録・更新、データモデルやレコードの自動取得、テナントの最新の設定との自動同期はできない | ルールは「設定方法」の手順に沿って、Configure Business Rules で手作業で作る。データモデルは `tools/build_catalog.py` で $metadata などから作り直すか、アプリで編集する |
| SuccessFactors との連携 | SuccessFactors に取り込めるファイル（ルールのインポート用のファイルなど）は出力しない | 出力するのは設計案の JSON と、データモデル（catalog.js）・変更ログだけ |
| SuccessFactors との連携 | 既存のルールの読み込みはできない（Configure Business Rules から書き出したルールや、ルールの一覧は取り込めない） | 既存のルールは、文章か JSON に書き直して「ルール検証」に貼り付ける |
| AI | AI を呼び出さない。設計案は自分で AI チャットに送り、回答を貼り付ける。AI の回答の質や、指示どおりの形式で返るかは保証しない | エラーや注意があるときは、修正プロンプトで AI に直させる |
| 検証の範囲 | 合格は「SuccessFactors で動く」保証ではない。アプリの中のデータモデルの範囲で、ルールとして成り立つかを確認するだけ | テナントの設定とデータモデルが違えば結果も違う。必ずテスト用のテナントで動かして確認する |
| 検証の範囲 | 要件の意図どおりか（業務ロジックの正しさ）は判定しない | 「前提」と「項目の解決」を読んで、要件と合っているか確認する |
| 検証の範囲 | 実際の社員データでルールを実行（シミュレーション）しない。条件に当てはまる社員の数や、設定される値の結果は出ない | テスト用のテナントで、ルールのトレース（Business Rule Execution Log）を使って確認する |
| 検証の範囲 | 1 つのルールだけを検証する。複数のルールの実行順（イベント事由の自動設定 → 入力チェック → ワークフローの決定など）、onChange のルールの連鎖、同じ項目を設定するほかのルールとの競合は見ない | 同じ HRIS 要素・オブジェクトに割り当てるルールは、まとめて見直す |
| 検証の範囲 | 権限（Role-Based Permissions）、データモデルの表示設定（Visibility）、国別のデータモデル（jobInfo_DEU など）は考慮しない | 項目を読み書きできるかは、テナントの権限とデータモデルの設定で確認する |
| 検証の範囲 | Message Definition・Workflow Configuration・Lookup テーブルの中身が、テナントに実際にあるかは確認できない（データモデルに登録がないため） | 「新規に必要な設定」に書かれたものを、先にテナントで作る |
| 検証の範囲 | 条件に関数を使った分岐では、矛盾や実行されない分岐を判定できない。集合フィルターで 1 件に絞れるかも、「等しい」の条件があるかで推定するだけ | 関数を使う条件と集合フィルターは、テスト用のテナントで結果を確認する |
| 書けないルール | アラート（Employee Central・MDF）、Execute（Intelligent Services のイベントなど）、Add To / Remove From のアクションは、設計案 JSON で書けない。これらのシナリオでは条件だけを検証する | アクションは SAP の画面で設定する |
| 書けないルール | ルールのコンテキスト（Data Operation、Enable on Import、New Hire/Rehire UI など）、Original Record・Previous Value・前後の有効日付のレコード、有効日付で複数のバージョンを持つルール（Start Date の違うレコード）は書けない | 必要なら SAP の画面で追加する。設計案の「前提」に書いておく |
| 対象外のシナリオ | Position Management・Time Off・Recruiting・Onboarding・Compensation・Payroll などのモジュール固有のルールシナリオと関数は対象外。関数表はモジュールに依存しない汎用の関数だけ | 必要な関数は、SAP の公式ドキュメントで確認して `data/knowledge.js` に追加する |
| 対象外のシナリオ | Employee Central の特定用途のシナリオ（Generate Employee ID for Hire/Rehire、Calculate Full-Time Equivalent、Off Cycle Event Batch など）は、base object と Model だけを確認する | ルールの中身は SAP のドキュメントで確認する |
| 仕様の根拠 | ルールシナリオ・event・MDF の目的は SAP の公式ドキュメント（2611 版）に基づく。今後のリリースで変わることがある。次の 2 点は推定を含む：MDF の Insert イベントで使える目的（ドキュメントの表の読み取りによる）、Foundation Object のルールを割り当てる画面 | 新しいリリースのドキュメントが出たら、`data/knowledge.js` を見直す |
| データの共有 | アプリで行ったデータモデルの変更は、このブラウザにだけ保存される。ほかの人や別の PC には自動で反映されない | 管理パネルで catalog.js か変更ログを書き出して共有する（「3.6 データモデルの変更を全員に反映する」） |
